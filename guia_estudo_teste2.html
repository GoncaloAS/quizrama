🧵 Threads

1. Conceito de thread

Tradicionalmente um processo é um programa em execução com uma única thread (single thread of execution) — só pode fazer uma tarefa de cada vez. Os SO modernos estenderam o processo para suportar múltiplas threads de execução dentro do mesmo processo, permitindo realizar mais do que uma tarefa em simultâneo.

  • Single-threaded: uma só thread por processo; o conceito de thread nem sequer é reconhecido.
  • Multithreading: capacidade do SO de suportar múltiplos caminhos concorrentes de execução dentro de um único processo.

Motivação: a maioria das aplicações é um conjunto de várias tarefas. Tarefas independentes ou eventos assíncronos podem ser intercalados atribuindo uma thread a cada tarefa/tipo de evento.

Partilhado vs privado (o ponto mais cobrado): entre threads do mesmo processo são partilhados o código (text), dados, heap, ficheiros abertos e sinais. São privados de cada thread o TID, o conjunto de registos (incluindo o program counter), a stack, a prioridade/política de escalonamento e os dados específicos da thread.

2. Benefícios & implicações de desempenho

Os 4 benefícios principais do multithreading:

  1. Performance (desempenho): criar e gerir threads é mais barato do que processos; o thread switch tem menos overhead do que o context switch entre processos.
  2. Resource Sharing (partilha de recursos): as threads partilham por omissão a memória (mesmo espaço de endereçamento) e os recursos do processo; entre processos seriam precisos mecanismos complexos do SO.
  3. Responsiveness (capacidade de resposta): numa aplicação interativa, o programa continua a correr mesmo que parte esteja bloqueada ou a fazer uma operação demorada — crucial para interfaces de utilizador.
  4. Parallelism (paralelismo): um processo single-threaded corre num só processador; com threads, estas podem correr verdadeiramente em paralelo em vários cores.
Concorrência ≠ paralelismo: concorrência é intercalar tarefas (possível mesmo num único core); paralelismo é correr ao mesmo tempo de verdade e exige múltiplos processadores/cores.

É mais eficiente implementar unidades de execução relacionadas como threads do que como processos separados: é mais rápido criar, terminar e trocar (switch) entre threads, e a comunicação entre threads é mais eficiente (a comunicação entre processos normalmente exige a intervenção do kernel).

3. Contexto de execução · TCB vs PCB

Uma thread é a informação necessária para representar um contexto de execução dentro de um processo: TID, prioridade/política de escalonamento, conjunto de registos (incl. PC), stack e dados específicos da thread.

A informação de execução fica guardada fora do PCB, num Thread Control Block (TCB) por cada thread:

TCB (por thread)PCB (por processo)
Thread ID, estado (Ready…)PID, User ID, Group ID
Program Counter (PC)Address space
RegistosOpen files, network sockets
Ponteiro para o PCBPonteiro para a lista de TCBs

Ou seja: cada TCB aponta para o seu PCB, e cada PCB aponta para a lista dos seus TCBs.

4. Estados de uma thread

Como nos processos, há 3 estados: Running (a executar), Ready (à espera de processador) e Waiting/Blocked (à espera de um evento). Há 4 operações que mudam o estado:

  • Spawn — cria-se uma nova thread (recebe contexto de registos e stack; vai para a ready queue).
  • Block — a thread espera por um evento (guarda registos e stack pointers).
  • Unblock — ocorre o evento esperado; a thread volta à ready queue.
  • Finish — a thread termina (registos e stack são desalocados).
Armadilha: são 3 estados mas 4 operações — não confundir as contagens.

5. Context switch de threads

Com threads, as scheduling queues passam a apontar para TCBs; trocar de thread implica guardar o contexto da atual no seu TCB e carregar o da próxima a partir do TCB dela.

  • Entre duas threads do mesmo processo: não é preciso mudar o espaço de endereçamento → mais barato.
  • Entre threads de processos diferentes: tem de mudar o address space, podendo invalidar a cache ou gerar page faults → mais caro.

6. Bibliotecas de threads

Uma thread library dá a API para criar/gerir threads. Dois tipos:

  • User-level (user threads): geridas em user space, sem suporte do kernel; chamar a biblioteca é uma chamada de função local (não uma system call).
  • Kernel-level (kernel threads): suportadas e geridas pelo SO; chamar a biblioteca resulta numa system call.

Todos os SO atuais (Windows, Linux, macOS, Solaris) suportam kernel threads. As três bibliotecas principais:

BibliotecaNível
POSIX PthreadsUser-level ou kernel-level
Windows ThreadsKernel-level
Java ThreadsGeridas pela JVM (usam a biblioteca do host)

7. Modelos de multithreading

Relação entre user threads e kernel threads — três formas:

ModeloMapeamentoParalelismoBloqueioExemplos
Many-to-Onemuitas user → 1 kernelSem paralelismo realuma a bloquear bloqueia todasSolaris Green Threads, GNU Portable Threads
One-to-One1 user → 1 kernelSimbloqueio de uma não bloqueia as outrasLinux, Windows NT/XP/2000, Solaris 9+
Many-to-Manymuitas user → nº ≤ de kernelaté ao nº de kernel threadskernel escalona outra ao bloquearSolaris < 9, Windows ThreadFiber
One-to-one: permite paralelismo real, mas o overhead de criar muitas kernel threads faz a maioria das implementações limitar o número de threads. Many-to-many combina o melhor: muitas user threads + paralelismo limitado sem o bloqueio total do many-to-one.

8. Pthreads — create / exit / join

pthread_create(&tid, &attr, runner, arg);  // attr=NULL -> atributos por omissão
pthread_exit(rval_ptr);                      // termina SÓ a thread
pthread_join(tid, &rval_ptr);                // espera (bloqueia) que tid termine
  • pthread_create: a nova thread executa start_rtn(arg); o TID fica em tidp; attr=NULL usa os atributos por omissão. Retorna 0 em sucesso, número de erro em falha.
  • pthread_join(tid, rval_ptr): bloqueia até tid chamar pthread_exit() ou retornar da sua rotina; o código de retorno fica em rval_ptr.
Armadilha clássica: pthread_exit() ou um simples return da rotina inicial termina apenas a thread. Mas se uma thread chamar exit(), termina o processo inteiro (todas as threads). No exemplo dos slides, a variável sum é global e partilhada entre as threads.

9. Semântica de exec() e fork() com threads

  • exec() numa thread → substitui o processo inteiro, incluindo todas as threads.
  • fork() tem tipicamente duas versões: (a) duplica todas as threads (novo processo multithreaded); (b) duplica só a thread chamadora (novo processo single-threaded).

📁 Sistema de Ficheiros

10. Ficheiro, atributos e tipos

O sistema de ficheiros (FS) é a parte mais visível do SO. Tem duas partes: uma coleção de ficheiros (cada um uma unidade lógica de armazenamento) e uma estrutura de diretórios. O FS abstrai as propriedades físicas dos dispositivos, que são não voláteis (o conteúdo persiste entre reinícios).

Atributos típicos de um ficheiro: Name, Type (muitas vezes a extensão), Location (ponteiro para o sítio no dispositivo), Size, Protection (quem pode ler/escrever/executar) e Time/date/user-id.

Exemplos de tipos: executable (exe, bin), object (obj, o), source (c, java), batch (bat, sh), library (lib, a, so, dll), archive (zip, tar), multimedia (mp3, avi)…

11. Acesso e proteção

Padrões de acesso a um ficheiro:

  • Sequencial: bytes lidos/escritos por ordem (a maioria dos acessos).
  • Aleatório/direto: bytes lidos/escritos sem ordem (sem ter de ler tudo até ao ponto desejado).

Direitos de acesso (proteção): Read, Write, Execute, Append (escrever só no fim), Delete e List.

Append vs Write: append acrescenta apenas no fim do ficheiro; write escreve/reescreve.

12. Organização: partições e volumes

Um dispositivo pode ser usado inteiro ou subdividido em partições. Uma partição sem FS (raw partition) serve para swap ou bases de dados que formatam os dados à medida. Um volume é a entidade que contém um FS — pode ser um dispositivo inteiro, parte de um, ou vários dispositivos ligados.

EstruturaConteúdoNomes alternativos
Boot control block1.º bloco do volume; info para arrancar o SOboot block (UFS) · partition boot sector (NTFS)
Volume control blocknº total de blocos, blocos livres, tamanho de bloco, ponteirossuperblock (UFS) · parte da master file table (NTFS)
Directory structureorganiza diretórios e ficheirosparte da master file table (NTFS)

13. Diretórios e links

A estrutura de diretórios é como uma tabela de símbolos que traduz nomes → entradas de diretório. Deve permitir inserir/apagar/procurar/listar, ser eficiente e conveniente.

  • Tree-structured: raiz única, cada ficheiro com um path name único. Cada processo tem um diretório atual. Caminho absoluto (começa na raiz, ex.: /spell/mail/exp) vs relativo (a partir do diretório atual).
  • Acyclic-graph: permite partilhar ficheiros/subdiretórios via links (ponteiros/path names). Um ficheiro passa a ter vários caminhos absolutos.
  • General graph: permite ciclos → problemas: difícil saber se se pode apagar; o contador de referências pode nunca chegar a 0 (referências circulares); pode ser preciso garbage collection. Evita-se permitindo links só a ficheiros, não a subdiretórios.
Symbolic link vs hard link (na eliminação):
• Symbolic link: apagar o link não afeta o original; apagar o original deixa os links inválidos ("illegal file name").
• Hard link: mantém-se um contador de referências; o ficheiro só é apagado quando o contador chega a 0.

14. Ficheiros abertos · FCB

Para evitar procurar a entrada do ficheiro a cada operação, usa-se open() antes do primeiro uso. open() devolve um índice para a per-process open-file table — chamado file descriptor (UNIX) ou file handle (Windows). Há duas tabelas:

System-wide open-file tablePer-process open-file table
Independente do processoEspecífica de cada processo
FCB (file control block) — evita ler do disco a cada operaçãoReferência à entrada na system-wide
File-open count — quantos processos têm o ficheiro aberto (remove o FCB quando o último fecha)Modo de acesso + file pointer (última posição de leitura/escrita)

O FCB contém: permissões, datas, dono/grupo/ACL, tamanho e ponteiros para os blocos de dados.

15. Montagem e VFS

Tal como um ficheiro tem de ser aberto, um FS tem de ser montado (mount) antes de acedido. O SO recebe o nome do volume e o mount point (localização onde o FS é anexado), tipicamente um diretório vazio.

O Virtual File System (VFS) é uma camada que permite usar a mesma interface (open/read/write/close) para vários tipos de FS, separando interface da implementação e despachando as chamadas para a implementação certa. Assenta numa estrutura única chamada vnode.

16. Alocação de espaço em disco

Objetivo de desenho: usar o disco eficientemente e aceder rápido. Três grandes métodos:

MétodoComo funcionaAcesso aleatórioFrag. externaCrescer
Contíguastart + length; blocos seguidosimediato: bloco B+NSim (precisa desfragmentar)Difícil (saber tamanho à priori)
Ligada (linked)cada bloco aponta para o seguinte; fim = nil (−1)mau: seguir N ponteirosNãoFácil
FATtabela no início do volume, 1 entrada por blocoeficiente (sobretudo com FAT em cache)NãoFácil
Indexadaindex block = array de ponteirosvia index blockNãoFácil
  • Contígua: mínimo de seeks; mas tem fragmentação externa e é difícil fazer crescer.
  • Ligada: sem fragmentação externa, fácil de crescer; mas desperdiça espaço em ponteiros (ex.: ponteiro de 4 bytes num bloco de 512 → 0,78% do disco) e o acesso aleatório é péssimo. A FAT resolve o desperdício (ponteiros ficam na tabela, não nos blocos de dados).
  • Indexada: cada ficheiro tem um index block; para ficheiros grandes usa-se esquema ligado, índice multinível ou inodes UNIX.
Índice multinível (números): bloco de 4 096 B → 1 024 ponteiros de 4 B. Dois níveis → 1 024×1 024 = 1 048 576 blocos → ficheiro até 4 GB.
Inodes UNIX: esquema combinado — vários ponteiros diretos + os 3 últimos ponteiros são single indirect, double indirect e triple indirect, permitindo ficheiros enormes.

💽 Dispositivos de Armazenamento

17. HDD e SSD

Um HDD grava dados magneticamente em pratos (platters) que rodam. Estrutura:

  • Track (pista): pista circular concêntrica — milhares por prato.
  • Sector (sector): subdivisão da track (centenas por track) — unidade mínima de leitura/escrita.
  • Cylinder (cilindro): conjunto de tracks na mesma posição do braço em todos os pratos.
  • Componentes: spindle, arm assembly, arm, read-write head (uma por superfície).
SSD vs HDD: o SSD é memória não volátil sem partes móveis. Vantagens: mais fiável (sem partes móveis), mais rápido (sem seek time nem latência rotacional), menos energia. Desvantagens: menos capacidade, mais caro por MB, tempo de vida potencialmente menor.
Armadilha: uma track está num só prato; um cilindro é o conjunto de tracks alinhadas em todos os pratos.

18. Transferências e latências

O disco liga ao computador por um I/O bus (SATA, USB, SCSI…). As transferências são feitas por controllers: o host controller (no computador) envia o comando ao disk controller (no disco), que opera o hardware. Os dados passam pela cache do disk controller.

Uma operação de I/O tem 5 fases (a disk latency é a soma de todas):

  1. Queuing time — o device driver processar o pedido.
  2. Controller time — o controlador executar a operação.
  3. Seek time — mover o braço até ao cilindro desejado.
  4. Rotational latency — o sector rodar até à cabeça.
  5. Transfer time — transferir os dados.
ValorTípico
Average seek time3–12 ms
15 000 RPM4 ms/rotação → 2 ms de latência rotacional média
10 000 RPM6 ms/rotação → 3 ms de latência rotacional média
Transfer rate50–100 MB/s
Regra: latência rotacional média = metade do tempo de uma rotação completa.

19. Desempenho (cálculos típicos)

Pressupostos: transfer rate 100 MB/s, sector 1 KB (transferir 1 KB ≈ 0,01 ms), disco 15 000 RPM (2 ms latência média, 3 ms seek médio).

CenárioTempoTaxa efetiva
Sector em local aleatório do disco3 + 2 + 0,01 = 5,01 ms~200 KB/s
Sector aleatório no mesmo cilindro (sem seek)2 + 0,01 = 2,01 ms~500 KB/s (2,5× melhor)
Sector seguinte na mesma track0,01 ms100 MB/s (200× melhor)
Conclusão: a chave é minimizar os atrasos de seek e rotacionais. Por isso a alocação contígua de ficheiros gera pedidos próximos (pouco movimento), enquanto ligada/indexada pode espalhar os blocos (mais movimento).

20. Escalonamento de disco

O SO mantém uma fila de pedidos por disco. Os algoritmos otimizam tipicamente só as tracks pedidas (ignoram sectores) e só fazem sentido quando há fila. Exemplo comum: fila 98, 183, 37, 122, 14, 124, 65, 67, cabeça em 53, cilindros 0–199.

AlgoritmoIdeiaMovimento totalPrós / Contras
FCFSordem de chegada640+ justo / − seeks longos
SSTFpedido mais próximo da cabeça236+ reduz seeks / − starvation
SCAN (elevador)varre até ao fim e inverte236+ poucos seeks, sem starvation / − favorece tracks do meio
C-SCANserve só numa direção; salta ao início382+ espera mais uniforme / − seeks longos no regresso
C-LOOK / LOOKcomo C-SCAN/SCAN mas não vai até ao fim físico322 (C-LOOK)+ evita seeks inúteis
Armadilhas: neste exemplo SSTF e SCAN dão o mesmo valor (236); C-SCAN (382) > C-LOOK (322). SSTF pode causar starvation; SCAN/LOOK/C-LOOK não. FCFS é o único descrito como justo.

Discos modernos: a latência rotacional pode ser quase tão grande como o seek; como o disco não expõe a localização física dos blocos lógicos, o escalonamento move-se para o hardware do controlador (o SO envia batches). SSD scheduling: sem cabeças móveis, a maioria usa FCFS; como as escritas não têm tempo uniforme (flash), alguns escalonadores juntam escritas adjacentes e mantêm as leituras em FCFS.

🧮 Gestão de Memória

21. Fundamentos & proteção (base/limit)

Só a memória e os registos são acessíveis diretamente pelo CPU. A memória é acedida pelo memory bus (vários ciclos → o CPU pode fazer stall); a cache entre memória e registos acelera os acessos e é gerida pelo hardware, sem o SO.

Cada processo precisa de um espaço de memória separado. A proteção tem de ser feita por hardware (não pelo SO, por desempenho). Um par de registos define o espaço:

  • Base register: menor endereço físico legal.
  • Limit register: tamanho da gama.

O hardware compara cada endereço: se base ≤ addr < base+limit permite; senão dispara um trap (addressing error). Os registos são carregados do PCB no context switch e o utilizador não os pode alterar.

22. Endereços lógicos vs físicos · binding

  • Endereço lógico: gerado pelo CPU.
  • Endereço físico: visto pela unidade de memória.
Binding de endereços (muito cobrado): em compile time e load time os endereços lógico e físico são IGUAIS; só em execution time ficam DIFERENTES (requer relocação dinâmica / MMU).

23. MMU e relocação

A MMU é o hardware que, em run time, mapeia endereços lógicos para físicos. No esquema base, o relocation register é somado a cada endereço lógico. O programa só vê endereços lógicos (0..Max); nunca vê os físicos (B..B+Max).

relocation register = 14000
endereço lógico 346  →  físico = 14000 + 346 = 14346

24. Swapping

Swapping: mover temporariamente processos de memória para um backing store (disco rápido) e trazê-los de volta. Permite que o espaço total dos processos exceda a memória física.

  • A maior parte do tempo de swap é transfer time, proporcional à quantidade de memória swapped → context-switch time elevado.
  • Um processo não precisa de voltar aos mesmos endereços físicos (se houver alocação dinâmica via relocation register).
  • Um processo com I/O pendente só pode ser swapped out com double buffering (I/O para buffers do kernel).

25. Alocação contígua · first/best/worst-fit

Na alocação contígua cada processo ocupa uma única secção contígua. Memória dividida em partições (fixas, ou variáveis ao tamanho do processo); o kernel regista as zonas livres (holes). Quando um processo termina, holes adjacentes são combinados.

Problema de alocação dinâmica — estratégias:

EstratégiaEscolhe…Nota
First-fito primeiro hole suficientegeralmente o mais rápido
Best-fito menor hole suficientetem de pesquisar tudo; menor leftover
Worst-fito maior holemaior leftover; pior dos três
Simulações: first-fit e best-fit são ambos melhores que worst-fit (velocidade e espaço); first-fit costuma ser mais rápido que best-fit.

26. Fragmentação interna vs externa

Interna: memória alocada mas não usada DENTRO de uma partição/frame (ex.: alocou-se um bloco de 1000 B para um pedido de 998 B). A paginação sofre disto (em média ~meia página por processo).
Externa: espaço livre total suficiente, mas espalhado em pedaços não contíguos. A alocação contígua e a segmentação sofrem disto; a paginação não.

Soluções para a externa: compactação (mover memória para juntar os holes — só possível com alocação dinâmica em execution time; pode ser cara) ou esquemas não contíguos (segmentação, paginação).

27. Segmentação

A segmentação encaixa na visão do programador: o espaço lógico é uma coleção de segmentos de tamanho variável (main, stack, heap, funções…). Endereço lógico = <segment-number, offset>.

  • Segment table (no PCB): cada entrada tem base (endereço físico inicial) e limit (comprimento). STBR aponta para a tabela; STLR dá o nº de segmentos (S legal se S < STLR).
  • Tradução: se offset < limit[s] → físico = base[s] + offset; senão trap.
  • Vantagens: partilha de segmentos; swap independente. Desvantagens: sofre do problema de alocação dinâmica (fits) e de fragmentação externa.

28. Paginação

A paginação permite espaço físico não contíguo. Comparada com a segmentação: torna alocação/swapping mais fáceis, evita fragmentação externa, não precisa de compactação e o hardware é mais simples (não compara com um limit). Por isso é usada em quase todos os SO.

  • Memória lógica em páginas; memória física (e backing store) em frames do mesmo tamanho (potência de 2). Carregar N páginas → encontrar N frames livres (não têm de ser contíguos).
  • A page table mapeia página → frame.
Divisão do endereço: se o espaço lógico é 2m e a página é 2n bytes, os m−n bits altos são o page number (p) e os n bits baixos o page offset (d).
Tradução: físico = frame × tamanho_da_página + offset.
Página de 4 bytes; page table {0→5, 1→6, 2→1, 3→2}
lógico 2  (pág 0, off 2) → 5×4 + 2 = 22
lógico 5  (pág 1, off 1) → 6×4 + 1 = 25
lógico 15 (pág 3, off 3) → 2×4 + 3 = 11

Fragmentação interna na paginação — ex.: página 2 048 B, processo 72 766 B = 35 páginas + 1 086 B → 36 frames; desperdício = 2 048 − 1 086 = 962 B. Tamanho da página: pequena → menos frag. interna mas page tables maiores e I/O menos eficiente; típico hoje 4 KB a 8 KB.

29. TLB e Effective Access Time

Sem ajuda, cada acesso exigiria 2 acessos à memória (page table + dados). A TLB é uma cache associativa pequena (64–1024 entradas) que compara todas as keys em simultâneo, sem penalização (faz parte do pipeline):

  • TLB hit: o frame está logo disponível (1 acesso à memória — os dados).
  • TLB miss: vai à page table em memória e adiciona o par à TLB (2 acessos).
EAT = HitRatio × (TLB + mem) + MissRatio × (TLB + 2×mem)
TLB=20 ns, mem=100 ns
Hit 80%: 0,80×(20+100) + 0,20×(20+200) = 96 + 44 = 140 ns
Hit 98%: 0,98×(120)    + 0,02×(220)    = 117,6 + 4,4 = 122 ns

30. Estruturas de page table · paginação + segmentação

Uma page table pode ser enorme: 32 bits + página 4 KB → 220 entradas × 4 B = 4 MB. Registos rápidos não são viáveis → a tabela fica em memória, com PTBR (base) e PTLR (tamanho). Dois problemas e duas soluções:

  • Memória cara da tabela → hierarchical paging (page table de page tables; só se aloca o necessário). Em 32 bits: [p1=10 | p2=10 | d=12] (210×4 B = 4 KB). Custa um acesso extra por nível. Em 64 bits são precisos vários níveis (o x86-64 usa 48 bits e 4 níveis).
  • Dois acessos por referência → TLB (ver §29).

Paginação + segmentação: processo = segmentos de tamanho variável, cada um dividido em páginas fixas. Endereço = <segment, page, offset>; uma segment table por processo + uma page table por segmento. Evita fragmentação externa e permite partilha aos dois níveis (segmento inteiro ou frame individual).

CONJUNTO #10 · CAPÍTULO 10

🪄 Memória Virtual

31. Conceito e demand paging

O programa inteiro raramente é todo usado ao mesmo tempo (código de erros raros, estruturas sobredimensionadas…). Memória virtual = técnica que permite executar processos que não estão inteiramente em memória.

Benefícios: menos uso de memória; criação de processos mais eficiente; menos I/O para carregar/swap; mais programas concorrentes; e o espaço lógico pode ser muito maior que o físico.

Demand paging: carregar uma página só quando é necessária (regra 90-10: 90% do tempo em 10% do código). Páginas nunca acedidas nunca são carregadas; quem está fora reside em memória secundária (disco).

32. Page fault e bit válido-inválido

Associa-se um bit válido-inválido a cada entrada da page table (inicialmente tudo inválido):

  • v (válido): a página está em memória e é legal.
  • i (inválido): a página está no disco ou não é legal (fora do espaço de endereçamento).

Um page fault ocorre quando o hardware acede a uma página marcada inválida (trap para o SO). Tratamento:

  1. Verificar no PCB se o acesso é legal (ilegal → terminar o processo).
  2. Encontrar um frame livre e trazer a página do backing store.
  3. Repor a page table (página agora em memória, bit → v).
  4. Reiniciar a instrução que causou o fault.

33. EAT do demand paging

EAT = (1 − p) × tempo_acesso_memória + p × tempo_de_page_fault, onde p é a probabilidade de page fault.

O page-fault service time tem 3 tarefas: atender a interrupção (1–100 µs), ler a página (5–10 ms, a mais lenta) e reiniciar o processo (1–100 µs).

mem = 200 ns, page-fault service = 8 ms = 8 000 000 ns
EAT = 200 + p × 7 999 800  (ns)
p = 0,001  → 8 199,8 ns ≈ 8,2 µs  (≈ 41× mais lento!)
<10% degradação → p < 0,0000025  (1 fault em 400 000 acessos)

Conclusão: a taxa de page faults tem de ser muito baixa.

34. Substituição de páginas (page replacement)

Se não há frame livre, faz-se page replacement: escolher uma victim page, escrevê-la no disco, trazer a desejada e atualizar a page table. São 2 transferências (out + in) → duplica o service time.

Dirty (modify) bit: marca-se quando a página é escrita. Se a victim page não foi modificada (clean), não é preciso escrevê-la de volta ao disco (já lá está) → poupa uma transferência. Objetivo de qualquer algoritmo: minimizar o número de page faults.

35. Algoritmos: FIFO · OPT · LRU

Avaliam-se correndo o algoritmo sobre uma reference string (só números de páginas) e contando page faults. Aceder de novo à mesma página em memória não causa fault.

  • FIFO: substitui a página mais antiga (fila: entra na cauda, sai pela cabeça). Simples, mas pode ser mau.
  • OPT (ótimo): substitui a página que só será usada mais tarde (ou nunca). Tem a menor taxa de faults possível, mas é impossível de implementar (não se lê o futuro) — serve de referência.
  • LRU (least recently used): substitui a que não é usada há mais tempo ("OPT a olhar para trás"). Bom, mas melhor que FIFO e pior que OPT. Implementa-se com contadores (time-of-use; procura na substituição) ou com stack (LRU sempre no fundo; sem procura, mas atualização mais cara).
Exemplo (3 frames, string A B C A B D A D B C B): FIFO = 7 faults; LRU = 5; Second Chance = 5; Aging = 5.

36. Aproximações a LRU

LRU "puro" precisa de hardware a cada acesso (atualizar relógio/stack), o que seria ~10× mais lento. Usa-se um reference bit (R) (posto a 1 quando a página é acedida; sabemos se foi usada, não a ordem):

AlgoritmoIdeia
Second chanceFIFO + reference bit: se R=0 substitui; se R=1 limpa o bit e move para a cauda (dá 2.ª chance).
ClockImplementação eficiente do second chance: fila circular + ponteiro que avança limpando bits até achar R=0 (evita mover páginas).
NRUUsa (R,M) em 4 classes: (0,0) melhor para substituir < (0,1) < (1,0) < (1,1) pior. Substitui a classe não-vazia mais baixa.
LFU/NFUContador por página somando o reference bit a cada tick; substitui o de menor contagem. Problema: página muito usada no início fica "presa".

37. Alocação de frames

É preciso alocar a memória física (fixa) entre processos, com um mínimo de frames por processo:

  • Equal: quota igual a todos (100 frames, 2 processos → 50 cada).
  • Proportional: proporcional ao tamanho — frame_i = (tamanho_i / total) × frames (100 frames, processos de 20 e 180 páginas → 10 e 90).
  • Priority: proporcional à prioridade (ou prioridade + tamanho).
Global vs local replacement: Global — um processo pode "roubar" um frame a outro; maior throughput, mais comum, mas tempo de execução variável. Local — só do seu conjunto; desempenho consistente, mas pode subutilizar memória.

38. Thrashing · working set · PFF

Thrashing: o processo passa mais tempo a paginar do que a executar (poucos frames → page fault → substitui página de que logo precisa → fault outra vez…). Resultado: baixa utilização de CPU. No gráfico CPU × grau de multiprogramação, a utilização sobe e depois cai abruptamente quando começa o thrashing.

  • Working set: conjunto de páginas usadas numa janela de tempo Δ (aproxima a localidade). Demanda total D = Σ WSi; se D > frames totais → thrashing. Solução: suspender/swap out um processo. Δ pequeno demais não cobre a localidade; grande demais cobre várias.
  • Page-Fault Frequency (PFF): controla diretamente a taxa de faults com limites superior e inferior — taxa alta → dar mais frames; taxa baixa → tirar frames.

✍️ Perguntas abertas resolvidas

O exame tem 5 perguntas abertas (coloca-se só a resposta final, sem penalização). Estas são do estilo de cálculo mais provável.

P1 — Divisão de endereço (paginação)

Enunciado: espaço de endereçamento lógico de 32 bits e páginas de 4 KB. (a) Quantos bits para o offset? (b) Quantas entradas tem a page table?

(a) 4 KB = 212 → 12 bits de offset. (b) 32 − 12 = 20 bits de page number → 220 = 1 048 576 entradas.

P2 — Tradução de endereço (paginação)

Enunciado: páginas de 4 bytes; page table {0→5, 1→6, 2→1, 3→2}. Qual o endereço físico do endereço lógico 5?

Lógico 5 → página = 5÷4 = 1, offset = 1. Página 1 → frame 6. Físico = 6×4 + 1 = 25.

P3 — Effective Access Time com TLB

Enunciado: TLB = 20 ns, acesso à memória = 100 ns, hit ratio = 98%. Qual o EAT?

EAT = 0,98×(20+100) + 0,02×(20+100+100) = 117,6 + 4,4 = 122 ns.

P4 — EAT com demand paging

Enunciado: acesso à memória = 200 ns, page-fault service = 8 ms, p = 0,001. Qual o EAT?

EAT = (1−0,001)×200 + 0,001×8 000 000 = 199,8 + 8 000 = 8 199,8 ns ≈ 8,2 µs.

P5 — Contar page faults (FIFO vs LRU)

Enunciado: 3 frames, reference string A B C A B D A D B C B. Quantos page faults com FIFO e com LRU?

FIFO = 7; LRU = 5.

P6 — Fragmentação interna (paginação)

Enunciado: páginas de 2 048 B, processo de 72 766 B. Quantos frames e qual a fragmentação interna?

72 766 / 2 048 = 35 páginas + 1 086 B → 36 frames. Fragmentação interna = 2 048 − 1 086 = 962 B.

P7 — Escalonamento de disco

Enunciado: fila 98, 183, 37, 122, 14, 124, 65, 67; cabeça em 53. Movimento total da cabeça com FCFS e com SSTF?

FCFS = 640 cilindros; SSTF = 236 cilindros (SCAN também dá 236; C-SCAN = 382; C-LOOK = 322).

P8 — Tempo de acesso a disco

Enunciado: disco 15 000 RPM, seek médio 3 ms, transferir 1 KB ≈ 0,01 ms. Tempo para ler um sector num local aleatório?

15 000 RPM → 4 ms/rotação → 2 ms latência média. Tempo = 3 (seek) + 2 (rotacional) + 0,01 (transfer) = 5,01 ms.

P9 — Alocação proporcional de frames

Enunciado: 100 frames; processo A de 20 páginas e processo B de 180 páginas. Quantos frames para cada?

A = (20/200)×100 = 10 frames; B = (180/200)×100 = 90 frames.
